# Baby Justice review — 2026-09-12

## Scope and architecture

Baby Justice is a native SwiftUI iOS app with separate parent and child feature areas, observable view models, and a shared API client and session store. Its Spring Boot backend uses Java, PostgreSQL, Flyway migrations, and transactional domain services. Parents approve tasks before children receive points; children spend those points on individual rewards, which progress through purchase, delivery, and receipt. [DESIGN.md](DESIGN.md) defines the shared domain and API contract.

This review covers business correctness, session handling, and client/server consistency. The findings below remain open; the implementation work accompanying this review addresses layout. Evidence comes from source inspection, existing tests, the design contract, and, for the refund finding, locally available Hibernate source. The scenarios describe how to reproduce the findings; no destructive account operations, point mutations, purchases, or private API requests were executed to reproduce them. No tests were written or modified. Race conditions were analyzed rather than exercised against a running database. Source line numbers refer to the reviewed checkout and may move during subsequent edits.

P1 denotes a high-priority correctness or data-loss issue. P2 denotes a concrete issue requiring a normal-priority fix.

## Layout implementation and validation — 2026-09-19

The layout changes keep the iOS 17 deployment target and use container dimensions rather than device identifiers or orientation. The shared `BJScrollView` centers scroll content with a 720-point width limit; authentication forms use 520 points, while dashboards, children, and the reward grid can use up to 1024 points. Native lists and forms have matching width constraints, and backgrounds continue to fill their containers.

Dashboard statistics and child cards adjust their column count to available width and scaled text metrics. Statistics share row heights, and accessibility text sizes use a single column for statistics and the reward shop. The shop retains its lazy grid. The landing screen scrolls when space is short and uses `AnyLayout` to rearrange its existing content into columns on wider windows. Buttons and form fields use minimum heights so larger labels can grow. Navigation stacks and state ownership remain intact during resizing.

Toolbar add, cancel, and close actions now provide both a title and a system icon; cancel actions use semantic cancellation placement. Apple documents that title-only toolbar items do not appear in Duo's vertical presentation. These changes follow [Preparing your app for iPhone Duo](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo), while the adaptive column implementation handles finite, unspecified, and infinite proposals described by [SwiftUI Layout](https://developer.apple.com/documentation/swiftui/layout/sizethatfits(proposal:subviews:cache:)).

Validation performed:

- `git diff --check` passed. No test files were added or modified, and no business behavior was changed as part of the layout work.
- On September 12, the landing screen was launched and its screenshots visually inspected on iPhone 17 and iPad mini simulators. That inspection preceded the September 19 changes; it does not establish visual coverage of the final build or authenticated screens.

## Backend findings

### B1 — P1: Multiple refunds can lose part of the child's balance

**Scenario:** A child has 50 points and two purchases awaiting delivery. Detaching the child refunds 30 points and then 20 points in one transaction. Both refund entries are recorded, but the final balance can be 70 instead of 100.

**Evidence:** [ChildrenService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/children/service/ChildrenService.java:204), lines 204–212, loops through purchases and calls `PointsService.credit` for each. [PointsService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/points/service/PointsService.java:59), lines 59–62, refreshes the same managed child before every credit. That refresh overwrites the preceding unflushed balance change. The history and notification inserts use sequences and do not flush the child between iterations. Local Hibernate 7.2.7 source confirms that this refresh path reloads the entity without first flushing its pending changes.

**Suggested fix:** Acquire the child lock and refresh its balance once for the entire refund operation, then apply each refund to that managed balance while preserving individual transaction records.

### B2 — P2: Editing a reward during purchase can make a one-time reward available again

**Scenario:** A parent's edit reads an `ACTIVE` reward. A concurrent child purchase commits `PURCHASED`. The edit commits afterward and writes its stale `ACTIVE` status, allowing another purchase of the one-time reward.

**Evidence:** [RewardService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/reward/service/RewardService.java:62), lines 62–68 and 101–103, reads the reward without a lock. [Reward.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/reward/model/Reward.java:27) has neither optimistic versioning nor dynamic updates. The purchase lock in [PurchaseService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/reward/service/PurchaseService.java:101), lines 101–105, serializes purchases but does not prevent this stale full-row update.

**Suggested fix:** Serialize all reward mutations using the same locking protocol, or introduce optimistic versioning and handle conflicts consistently with the existing task implementation.

### B3 — P2: Editing a repeatable task rewrites the displayed history of completed work

**Scenario:** A child receives 10 points for an approved repeatable task. The parent later changes its name and value to 100 points. The old approved assignment now displays the new name and 100 points, while the points ledger correctly retains the original 10-point credit.

**Evidence:** [TaskAssignmentDTO.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/task/model/dto/TaskAssignmentDTO.java:23), lines 23–28, maps historical assignments from the current task name and points. [TaskService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/task/service/TaskService.java:78), lines 78–83, changes those values on active tasks, including previously completed repeatable tasks.

**Suggested fix:** Preserve the task name and awarded points on each resolved assignment, and use those values for history. Decide separately whether changes to an in-progress task should affect its eventual award; the confirmed finding concerns work already approved and paid.

### B4 — P2: Receipt notifications can disclose a previous family's purchase to the new parent

**Scenario:** Family A delivers a reward, then detaches the child. Delivered purchases intentionally survive detachment. The child joins family B and confirms receipt of that old reward. Parent B receives the notification containing the reward name, although the purchase belongs to A.

**Evidence:** [PurchaseService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/reward/service/PurchaseService.java:157), lines 157–164, derives the notification recipient from the child's current family and only checks for a missing family. The purchase's originating family is not checked.

**Suggested fix:** Scope receipt notifications to the purchase's originating family and explicitly handle the child having joined another family. Preserve the supported ability to confirm an already delivered purchase after detachment.

## iOS findings

### I1 — P1: Parent account deletion promises to preserve points that the backend deletes

**Scenario:** A parent reads the account-deletion confirmation, which says that children retain their points and history, and proceeds on that basis. The backend resets every child's balance to zero and removes their points history.

**Evidence:** [ParentSettingsView.swift](../baby-justice/Features/Parent/Settings/ParentSettingsView.swift:34), line 34, contains the incorrect promise. [FamilyService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/family/service/FamilyService.java:47), lines 47–58, invokes the family reset; [ChildrenService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/children/service/ChildrenService.java:131), lines 131–135, resets each child; [PointsService.java](/Users/needxmafia/IdeaProjects/baby-justice-backend/src/main/java/pl/dudios/babyjustice/points/service/PointsService.java:52), lines 52–56, deletes the transaction history and zeros the balance. This behavior matches the account-deletion section of the design contract.

**Suggested fix:** Correct the confirmation to explicitly state that child accounts and logins survive, but points become zero and history is deleted. Keep it distinct from detaching a single child, which preserves points and history.

### I2 — P2: Out-of-order responses can show one child's rewards under another child's selection

**Scenario:** Select child A, then B before A's reward request finishes. B's response arrives first, followed by A's. The picker remains on B while the list shows A's rewards; opening a row can lead the parent to edit or archive the wrong child's reward. History filters have the same stale-response problem.

**Evidence:** [ParentRewardsHomeView.swift](../baby-justice/Features/Parent/Rewards/ParentRewardsHomeView.swift:57), lines 57–78, starts independent tasks and assigns the returned rewards without verifying the selected child or archive filter. [ParentHistoryViewModel.swift](../baby-justice/Features/Parent/History/ParentHistoryViewModel.swift:45), lines 45–60, similarly publishes results without checking whether the filter has changed.

**Suggested fix:** Capture the child and filter identity for each request, and publish data, loading state, and errors only if that request is still current. Cancel superseded requests where appropriate.

### I3 — P2: Reopening a reward after an uncertain purchase result loses its idempotency key

**Scenario:** The server commits a repeatable reward purchase, but the response is lost. The screen reports a network error. The child leaves, reopens the reward, and retries, causing a second purchase and debit with a new token. Retrying within the original screen correctly retains the existing token.

**Evidence:** [RewardDetailView.swift](../baby-justice/Features/Child/Shop/RewardDetailView.swift:13), line 13, stores the UUID only in view-local state. Its purchase method, lines 156–166, reports failure without preserving the unresolved purchase outside the screen. Destroying and recreating the view creates a different UUID, so the backend cannot recognize the retry.

**Suggested fix:** Preserve unresolved purchase intents and their tokens beyond the screen's lifetime, scoped to the account and reward. Reconcile an uncertain outcome before treating the next attempt as a new purchase.

### I4 — P2: A delayed unauthorized response can log out a newly authenticated session

**Scenario:** Several requests use an expired token. The first `401` logs the user out. The user successfully logs in again, then a delayed `401` from another old request arrives and clears the new session.

**Evidence:** [APIClient.swift](../baby-justice/Core/Networking/APIClient.swift:363), line 363, retains only whether a request was authenticated. Lines 388–395 log out the shared session for an authenticated request's `401`, without checking which token or session issued that request.

**Suggested fix:** Capture the request's token or session generation and invalidate the session only if it still matches. Cancel or disregard requests belonging to a replaced session.
